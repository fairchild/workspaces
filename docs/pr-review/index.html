Understand the managed reviewer from the outside in.

The system is simpler when you keep one idea fixed: a ReviewRun is the source of truth. GitHub statuses, PR reviews, dashboard pages, and health scripts are projections or read surfaces around that run.

Layer 1

The mental model

Learn the system in three roles. The PR author watches for a quick pickup indicator. The operator reads ReviewRuns. The maintainer preserves the boundaries that keep the system understandable.

PR author

Did the system pick up my PR?

The fast signal is the WorkSpaces Managed Review status on the current head. Its details URL should open the ReviewRun page, not loop back to the PR.

Operator

What state is the run in?

Start with scripts/pr-reviewer-runs.py. It reports pickup, active execution, coalescing, completed intent, projection failures, and stale or superseded runs.

Maintainer

What boundary must stay clean?

The webhook classifies and claims runs. The agent returns intent. The broker projects. Health and dashboard surfaces explain without changing state unless an explicit repair or retry action is used.

Layer 3

Two lifecycle questions

Most confusion comes from treating execution and GitHub projection as one state. They are separate because the right recovery action is different.

Execution: did the agent produce usable intent?

Stored in status.

started

The run exists and execution or collection may still be active.

completed

The run has validated review intent. Publication is tracked separately.

failed

No usable intent exists. Retry only when safe and current-head.

superseded

Newer PR activity replaced this run. Do not retry it.

Projection: did GitHub receive the effect?

Stored in projection_status and projection records.

pending

Projection is not complete yet, usually because execution is still active.

projected

GitHub status and review have been applied for this run.

failed

Intent exists, but GitHub write failed. Repair without rerunning the agent.

superseded

Projection was intentionally skipped because newer work covers the PR.

Layer 4

Happy path in four moves

These are the normal transitions a healthy PR should show. The early pending status is useful because it proves pickup before the review exists.

  1. 1

    Webhook claims the work

    A material trigger creates a ReviewRun and publishes a pending status with a details URL.

  2. 2

    Managed agent executes

    The runtime stores the session id. Health may show the run as starting or running.

  3. 3

    Broker collects intent

    Completed session output becomes validated review intent on the ReviewRun.

  4. 4

    Broker projects to GitHub

    The PR review posts, the status flips success, and the projection ledger records the effects.

Layer 5

Drill into the details only when needed

The sections below are ordered from conceptual to operational. Open them as your questions get more specific.

What counts as a material trigger?

Material triggers are PR activity that should review or re-review code: opened, reopened, ready for review, synchronize, eligible body or base edits, and evidence-bearing PR comments. Metadata-only noise is ignored before any ReviewRun claim happens.

Why coalesce active runs?

If a new material trigger arrives while the same PR and reviewer config already has an active run, the system records the latest coalesced trigger and head on the active run instead of starting parallel sessions. When the active run completes, stale output is suppressed and exactly one follow-up run covers the latest state.

Good outcome One active session at a time, latest head recorded, one follow-up if needed.
Bad outcome avoided Three overlapping reviews that race to comment on different PR heads.
What does the broker own?

The broker is the publishing boundary. It collects completed managed-agent output, validates review intent, persists completed ReviewRun state, suppresses stale output, posts GitHub reviews, updates commit statuses, and repairs failed projections from stored intent. The agent does not post directly to GitHub.

When do we retry versus repair?

Retry execution only when no valid review intent exists, the failure is retryable, and the run still targets the current PR head. Repair projection when status=completed but projection_status=failed; the stored intent should be applied to GitHub without rerunning the agent.

What should never be exposed?

Do not expose raw webhook payloads, secrets, tokens, or unbounded transcript dumps in learning docs, health output, projection records, or dashboard pages. Operator surfaces should show enough context to debug state without leaking credentials or sensitive session output.

Layer 6

When something looks wrong

Use the ReviewRun report first. Use the GitHub projection audit when the run report is healthy but GitHub appears out of sync.

Observation Interpret as First action
No ReviewRun row for an eligible trigger Pickup or ingestion gap Inspect missingRuns, then check trigger classification.
Pending status just appeared Pickup succeeded; execution or projection may still be active Wait inside SLO or open the details URL for run state.
Active run has coalesced fields Newer material trigger arrived during execution Let the broker suppress old output and start one follow-up run.
Completed run has failed projection Valid intent exists, GitHub projection failed Repair projection or let the repair sweep re-apply effects.
Superseded run Newer work intentionally replaced it Do not retry. Use the current-head covering run.

Operator commands

Commands worth memorizing

These are intentionally separate: one reads ReviewRuns, the other audits GitHub projection drift.

ReviewRun source-of-truth report

uv run --script scripts/pr-reviewer-runs.py

Use this first for pickup, active runs, stuck runs, completed runs awaiting projection, failed execution, failed projection, and superseded runs.

GitHub projection audit

uv run --script scripts/pr-review-health.py \
  --repo fairchild/workspaces \
  --updated-within-hours 72 \
  --pending-timeout-min 30

Use this after the run report when GitHub status or review state appears inconsistent with the ReviewRun source of truth.
