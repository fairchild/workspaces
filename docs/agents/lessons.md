# High-Signal Lessons Ledger

Master record of hard-won, repo-wide lessons: full statement, rationale, and history live here. Each lesson also fires as a compressed rule at the surface where it's needed — root `AGENTS.md` for lessons that must fire unconditionally at session start, a nested `AGENTS.md` for surface-specific ones. When editing a lesson, update both the ledger entry and its firing surface. When a lesson graduates to machinery (a CI gate, a script), delete its prose here and note the replacement.

## Unconditional — fire from root `AGENTS.md`

- **Every lane needing macOS is GitHub-hosted `macos-15`** — generic build/test, the UI smoke lane (`ui-smoke-advisory.yml`), agent evidence (`_evidence.yml`), and release/signing/notarization; agent and metadata jobs run `ubuntu-latest`. No self-hosted runner is registered for this repo at all — `blue-workspaces` was deregistered on 2026-08-13, after `lume-macos` and `tart-ui` — so `.github/actionlint.yaml` allows no self-hosted label and a `runs-on` naming one fails lint. Reaching for `signing-host` does not fall back to hosted; it queues forever. Perf benchmarks are not a CI lane: they run laptop-local, opt-in per run, per `docs/decisions/perf-measurement-laptop-optin.md`.
- **Ship a diagnostic probe instead of your third guess.** Terminal arc #306→#309: two guess-fixes merged green and failed in production; one temporary probe (#308) revealed the root cause in a single ship cycle. When you're guessing, stop and instrument. Corollary from #1251: instrument the boundary you *lack*. Four passes chased a launch residual that `terminal_first_output` had been localizing on every run since the investigation opened — the probe that finally settled it only earned its place by timing a hop nothing measured yet. Read the sub-metrics already being collected before adding more.
- **A clean rebase across a rename is not evidence the tests still test anything.** #1393 rebased over #1389's rename of `latest_completed_check_run` to `check_runs_for`: git had nothing to conflict on, the four new tests kept patching the dead name, their mocks went inert, and the real `gh` subprocess path ran under green-looking tests. Re-run the full suite after any rebase — "Successfully rebased" describes the text, not the behavior.
- **The tracker lags the code — verify before planning from it.** Three grooming/planning passes in a row (2026-06-28 ×2, 2026-07-02) found open issues whose work had already shipped. Before sequencing work from open issues, `rg` the acceptance criteria against the tree; close what's done in the same cycle that ships it (`Closes #N` in every implementing PR).

## Desktop UI — fire from `Sources/AGENTS.md`

- **Keep terminal surfaces nearly chrome-free.** Repo overview pages can carry metadata and actions, but terminal views default to the canvas with minimal surrounding UI.
- **Prefer quiet discoverability over persistent controls.** Avoid right-click-only primary actions, but also avoid always-visible sidebar affordances that add noise. Hover-visible scoped actions are usually the right compromise.
- **Persist selection state by stable IDs, not live SwiftData objects.** Restore and fallback logic should resolve models late and validate them against current data before selection.

## Agent paths — fire from `web-next/AGENTS.md`

- **Vercel `Sandbox.create({env: {...}})` does NOT propagate to `sandbox.runCommand()`.** Write env vars to an `env.sh` and `source` it at the top of the script. See `docs/development/agent-chat-sandbox.md` § "Claude CLI Authentication".
- **"Tests green" ≠ "works in production" for agent paths.** For changes touching `createSandbox`, `restoreSnapshot`, `createTerminalSandbox`, or `streamOutput`, send a real chat message in production and read the agent stream before declaring victory.

## Performance measurement — ledger only

- **A metric that shares a thread with the work it times can stop early, and the error flatters.** #1251: `launch_to_first_prompt` closed on a shell signal libghostty usually delivered through the main queue but occasionally raised inline — on the main thread, from inside a call the app itself had made mid-bring-up. Those samples closed the interval while the main thread was still ~400 ms from servicing anything, provable from the same sample's own queued ticks. Roughly one launch in ten landed there, and because it looked like the fast path, three passes read it as proof the 592 ms reference was achievable and kept rebuilding the reference on it. Contention between an instrument and its subject biases the error toward success — the one direction nobody investigates. Where a measurement can close on a path that bypasses the queue it normally waits on, a second independent signal is what separates "finished" from "measured wrong"; here a fixed-interval main-queue heartbeat, armed at launch, showed the main thread servicing nothing until long after the metric had stopped.
- **Re-derived references belong to a named protocol epoch, and comparisons across one are not app deltas.** The same #1251 fix moved *when* the launch metric closes, so post-fix numbers describe a different measurement than pre-fix ones even on identical code. `perf-baseline.sh` stamps `protocol_epoch` on every recorded row, the dashboard only takes a delta against a row of the same scenario and epoch, and `perf-compare.py` warns when a comparison spans either boundary. A reference that is only reachable by a measurement bug is retired rather than carried forward — keeping 592/631 would have preserved a target no honest sample could hit.

## Release and dev-machine ops — ledger only

- **Release version metadata must have one source of truth.** Tag, app version, and packaged artifact version should be validated against each other before a release is created. Graduated to machinery: `scripts/release-version.sh assert-tag-match`, and tag-driven releases fail fast on mismatch (`RELEASING.md`).
- **`git cherry` says "not merged" about work that is already merged.** The v0.26.0 release sweep found `fairchild/fix-automation-wait-flake` with four commits that `git cherry -v origin/main` marked `+`, meaning absent from `main`. All four had already landed — #1307 squashed three of them and #1317 took the fourth. `git cherry` compares patch-ids, so a squash, a rebase, or any edit made during review changes the patch and the original commit reads as unmerged forever. An old merge base compounds it: the three-dot diff then shows the same work as freshly added. Neither signal is evidence. Content is: `main` already contained `waitPatternMatchesWithoutTheMainActor` and the 60s `observationCeiling`, which settled the question in one grep. The branch held the *pre-review* version of work whose *post-review* version was already shipped, so merging it would have moved code backwards — the failure mode here is not a wasted merge but a silent regression that looks like catching up on a backlog. Before merging any branch that survived a review cycle, grep `main` for its distinctive symbols instead of trusting a commit-level ancestry check.
- **If the app opens or closes unexpectedly on a dev machine, check the launching process first.** CI/self-hosted runner behavior can look like an app bug.
- **Ship independent risky changes separately, especially in the release lane.** #1293 bundled three of them into one PR: a new UV-based release gate, a mise version pin, and moving the signing job from `[self-hosted, signing-host]` to `macos-15`. Each broke a different v0.24.0 attempt (fixed by #1297 and #1298), and because they shipped together every failure had three candidate causes. The release lane is the worst place to bundle, because it only executes on a tag push — so each defect costs a fix PR, a tag move, an owner approval, and a full build cycle just to discover the next one. A bundled change also outruns its own documentation: #1293 moved the runner without updating this ledger's runner rule, so for four days the code and the stated invariant contradicted each other (corrected in #1322).
- **Point an existing check at reality before building a new one.** All four v0.24.0 failures were cases where a check existed but ran where the risk wasn't: CI exercised PRs while the release lane's environment was only ever exercised by a release. The fix was not new machinery — `ci.yml` already path-triggered on the release files and already ran the same `macos-15` runner class, it just provisioned differently (#1303). A proposed rehearsal job and a preflight tool-inventory script were both cut on review as redundant: the rehearsal duplicated a lane that already exists (a `workflow_dispatch` of `release.yml` from `main` publishes a full signed, notarized tester prerelease, and says so in a `::notice::` on dispatch), and a hand-maintained list of required binaries would have been a second copy of the lane's contract — a fresh drift surface, in a fix whose whole diagnosis was drift. Corollary: new verification apparatus states what it replaces. If the checking apparatus is becoming its own maintenance project, propose less.
- **An environment secret shadows the repository secret of the same name — including when it is empty.** The fifth v0.24.0 attempt failed `Validate release secrets` on `APPLE_API_KEY_ID` and `APPLE_API_ISSUER_ID` after they were set on the `release` environment from a subshell that produced nothing: `gh secret set` accepts an empty value without complaint, and the empty environment copy silently overrode a working repository value. Reading the failure needs one trick — Actions masks non-empty secrets as `***`, so a secret printing *blank* in a log is present but empty, while a genuinely absent one also prints blank; only the contrast with neighbouring `***` lines distinguishes "empty" from "missing". `setup-release-secrets.sh` already refuses an empty issuer ID; the values were set by hand with `gh secret set`, going around that guard. Emptiness cannot be detected from outside — the secrets API returns only `name`, `created_at`, `updated_at` for both scopes, and in-workflow bash sees unset and empty as the same `""` — so #1323 fixed the failure message to name both causes and both scopes instead of asserting the value is missing.
- **A GUI app launched by launchd sees none of your shell's environment.** Dock/Finder/`open` hand the app launchd's bare environment (`PATH=/usr/bin:/bin:/usr/sbin:/sbin`, ~11 vars), so `.env` files, `~/.zshrc`, and a CLI wrapper that shells out to `/usr/bin/open` all fail to reach it; `launchctl setenv` from a login LaunchAgent is the bridge, with Keychain holding any secret at rest. This is why `scripts/launch-dev.sh` env vars work (it spawns the binary directly, `nohup env ... "$DEBUG_BINARY"`) while the `/Applications` copy started from the Dock ignores them. Mechanism, verification commands, and a worked third-party example: `docs/development/macos-gui-app-environment.md`.

## Factory operations — ledger only

- **The daily implementation budget counts `ready` applications, not admissions — a declined release still spends a slot.** `is_factory_implement_dispatch` (`scripts/factory-implement.py`) counts a run when the actor is the owner or the sweep **and** the run is a `workflow_dispatch` or its title starts with `Factory Implement ready #`. Label edits that produce other titles (`Factory Implement quality #1272`) cost nothing, so a triage sweep can fire dozens of instant-skips without touching the budget. Releasing an issue that is then declined does spend one. On 2026-08-29 #1368 was released, declined for having no `## Requested Evidence` section, given a contract, and released again: one issue, two of the day's six slots, one of them wasted. Write the evidence contract before the first release, never after. Two caps apply and both are shared across every lane: `FACTORY_IMPLEMENT_DAILY_CAP` defaults to 6 releases per day, and `FACTORY_WIP_CAP` is 2 concurrent claims. A batch release exhausts the daily pool long before the work-in-progress cap becomes the limit, so "release the queue" is never a one-day plan.
- **Applying `ready` puts an issue at the back of the queue, not the front.** `scripts/factory-sweep.py` selects with `sort=created&direction=asc`, so the sweep takes the oldest-created eligible issue first. On 2026-08-29 an owner decision to run #1428 (created that day) ahead of #1033 (2026-07-09) and #1267 (2026-08-08) would have inverted on contact with the queue: releasing #1428 last made it last. Moving work forward takes an owner `workflow_dispatch` on that issue, which bypasses the sweep's ordering, or removing `ready` from the older ones. Check the selection query before assuming a priority call survives. Related: a stale claim does not throttle one issue, it halves the factory — at a work-in-progress cap of 2, #1352 sat `claimed` for five days with no branch and no pull request, leaving one effective lane, and both releases made that morning deferred on "WIP cap is full" rather than on anything wrong with them. Check the age of `label:claimed` before diagnosing throughput.
